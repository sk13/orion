# OpenFHE backend

A second FHE runtime for Orion, selected with `backend: openfhe` in the config
(see `configs/mlp_openfhe.yml`). It implements the C ABI declared in
`orion/backend/c_api/orion_backend.h`, which is the same ABI the Lattigo (Go)
library exports, so the Python layers are shared by both backends.

## Build

Needs an OpenFHE >= 1.3 installation (developed against v1.6.1) and CMake.

```
cmake -S orion/backend/openfhe -B build -DCMAKE_PREFIX_PATH=/path/to/openfhe
cmake --build build
cp build/openfhe-linux.so orion/backend/openfhe/
```

`ORION_OPENFHE_LIB=/path/to/openfhe-linux.so` loads the library from elsewhere.

## Status

Working: encode/decode (real and complex), encrypt/decrypt, add/sub/mul with
scalars, plaintexts and ciphertexts, rotations, rescale, BSGS linear transforms
(double-hoisted), depth-optimal polynomial evaluation (Chebyshev and monomial,
same level consumption as Lattigo), (sparse) bootstrapping, and the `save`/`load` I/O
modes. The MLP, LoLA, HELRM and ResNet20 examples run end to end.

I/O modes (`io_mode: save` / `load`, as with Lattigo): the secret key, the rotation keys
and the encoded diagonals are written to the HDF5 files `keys_path` / `diags_path` and read
back per layer, so they do not all have to fit in RAM. ResNet20 needs about 125 GB of RAM
without them and about 55 GB with them, at the price of about 77 GB of files (64 GB of
diagonals, 13 GB of keys) and 50-70% more time. The files are only valid for the same
parameters and the same OpenFHE version (a mismatch is detected and reported). Polynomials
are stored as raw coefficients. A loaded secret key has no public key (OpenFHE cannot derive
one), so encryption then uses the secret key.

Minimax sign polynomials (the `ReLU` activation) are still generated by the
Lattigo library (a multi-precision Remez algorithm): the OpenFHE backend loads
`lattigo-linux.so` for that one function if it is present.

## Differences from Lattigo

* CKKS with `FIXEDMANUAL` scaling, so Orion keeps deciding when to rescale.
  OpenFHE tracks scales approximately in this mode; the backend keeps the exact
  scale of each ciphertext itself and corrects values on decode.
* Without bootstrapping, every `LogQ` entry after the first must equal `LogScale`
  (OpenFHE uses one scaling-modulus size).
* Bootstrapping (enabled when the config has a `boot_params` section, or with
  `ORION_OPENFHE_BOOTSTRAP=1`) reserves extra limbs at the top of the chain and one
  hidden limb at the bottom (OpenFHE consumes a level before raising the modulus).
  OpenFHE's fixed-scaling bootstrap is only accurate with a scale of about 2^52 or
  more and a 60-bit first prime (it fails outright at 2^40), so the backend then uses
  an internal scale of 2^59 (`ORION_OPENFHE_BOOT_SCALE`; 2^53 gives only ~11 bits after a
  bootstrap, 2^59 about 17) and maps Orion's default scale 2^LogScale onto it. Orion's
  levels and the moduli chain it sees are unchanged.
* OpenFHE has no conjugate-invariant ring. `RingType: ConjugateInvariant` with
  `LogN` is emulated with a standard ring of degree `2^(LogN+1)`, which gives the
  same number of slots (`2^LogN`) and the same rotation semantics.
* The secret-key Hamming weight (`H`) is ignored (uniform ternary key).
* Rotation-key ids exposed to Python are plain rotation amounts, not Galois
  elements.
